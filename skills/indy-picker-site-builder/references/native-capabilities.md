## Requested typography mapping

The optional `fd-typography/v1` heading/body/interface choices are a build request, not verified native capability. The current evidence does not establish three independent Theme & Style font-role controls. Inspect the destination's real font controls and each selected component's saved CSS/HTML before choosing the owner; source rules can explicitly set families and defeat a global choice.

Prefer the native field when it expresses the requested role. If a selected module needs scoped styles, prepare the narrow role mapping within its authorized Theme/Page/Section owners and retain the original field for rollback. Do not combine whole source stylesheets, inject a remote font import, or replace Material Icons/other native glyph fonts. The interface role describes visible navigation, button and control labels; it does not include every span or icon. Record any roles the editor couples together or cannot express, rather than silently substituting the source design.

Reopen the saved fields and verify computed family/fallbacks, text wrapping, navigation/button fit and form labels at desktop and actual phone width. Mark a role applied only from that target's saved and rendered evidence. Theme saves can take effect immediately; Page styles remain subject to their separate draft/publication state. Preserve the default draft stop and the user's existing scope.

At that initial pilot the public app displayed native 404, **Oops. Nothing here**, and Admin Pages was **No Pages**. TEMPLATE STANDARD did not copy design A or any Pages. ## Hosting is a separate layer

**Current naming policy:** preserve the nine working INDY Demo hosts. Replacement Showcase 193 uses `template-showcase-demo-indy-consumer.netlify.app`; the other eight use `template-<design>-indy-consumer.netlify.app`, with one-word Site/display names. Earlier Showcase 183/184 remain intact; the old unprefixed host is historical pilot evidence. The reference prefix is not a universal rule for customer builds. The user requires URL changes through **INDY Developer Site Settings**, without an external Netlify login. Record desired native fields and actual public identity separately; do not guess changes to Netlify IDs or Git branches.

The **historical Site 183 naming test** is recorded in repository-relative `evidence/website-templates-pilot/url-naming-journal.json`; it does not describe the later replacement Site 193:

- A Name-only save of `template-showcase` was rejected because **Hostname is required**, despite its initially auto-created blank value. Adding `https://template-showcase.netlify.app` allowed Save, and both fields persisted on reopen.
- That exact short URL served an **unrelated React/NFT site**. It was a collision, not a successfully renamed INDY consumer site.
- The corrective save restored **Netlify Site Name = `showcase-indy-consumer`** and explicitly set **Hostname = `https://showcase-indy-consumer.netlify.app`**, because blank was disallowed. Both persisted; Netlify Site ID and Git Branch Name remained unchanged. This was Site 183's restored working address.
- The longer `template-showcase-indy-consumer` Name and full Hostname were saved for **one explicitly approved Trigger Site Deploy test**, requested at **2026-10-26 01:06:14.767 UTC**. INDY reported Deploy Request Sent and roughly two minutes. A fresh public check after roughly four minutes still returned **Netlify Site not found**. A Success badge was observed for the unchanged Site ID, but no exact job/build ID was established and the candidate version link did not resolve. This did not verify a hostname rename, ownership or availability.
- After that test, the original working Name and full Hostname were restored and reopened/read back with the same Site ID and branch. That checkpoint established only Site 183's empty consumer shell, not a completed design.
- A further proposal with prefixed Name/Hostname and an empty Site ID was prepared **unsaved** and declined at that time. Reload discarded it. Later user consent authorized a separate new Showcase 193 in INDY Demo; it did not authorize re-provisioning or deleting the older shell. No old hosting proposal remains pending.
- Native Netlify Deploy Status and advanced choices were inspected; no rename control was observed and no advanced Execute action was pressed. Exactly one approved manual deploy was submitted in the naming phase. That approval does not authorize another deploy or a provisioning retry.

A successful native Save or deploy badge alone cannot close a hostname change. Verify native readback, exact public URL, intended Site identity and absence of an unrelated destination before using it in the Hub or reporting completion. Plan the desired prefix before new consumer-host creation. If INDY controls have not produced a verified result, report the capability gap within the requested Admin-only workflow rather than requiring provider login or assuming another deploy will rename the host. Keep the current nine hosts unchanged during content maintenance.

Observed **Developer → Developer Site Settings → Hosting**, route `#/developers/settings/site-settings`, contains Display Hostname, Hostname, Netlify Site Name / Netlify Subdomain (labels differ between retained screens), Netlify Site ID and Git Branch Name; actions Create Consumer Website, Preview Site and Trigger Site Deploy. Keep internal hosting identifiers in the private build journal, not the customer handoff.

Do not copy or guess these values. A View Page path containing `/null/` is not proof of missing hosting; inspect Hostname/Netlify Site Name or Subdomain read-only and verify an existing URL. Content Save, Page/Global Widget Publish, register-configuration push and Netlify deploy are different operations. Explicit consumer-site creation can initiate its first deploy; that does not authorize later manual Trigger Site Deploy actions. The Admin top-bar publish control can push register configuration and is not a website publish control. Do not use Trigger Site Deploy for ordinary saved drafts, a missing homepage or an automatic retry.
