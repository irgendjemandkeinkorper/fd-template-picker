# Module packaging and assembly

## Package the actual editable fields

Build a readiness row for each selected stable `optionId`, including globals and optional modules. Separate these levels: source screenshot checked; native fields captured; isolated module saved/read back; destination assembly verified; consumer desktop/phone/theme behavior verified. Do not collapse them into a generic “verified” flag.

A portable package needs:

- Native widget type and exact final internal Name plan for each ordered child Section; composite heroes A/C can contain more than one Section.
- Widget main settings, Section settings (visibility, devices, scheduling, width/margins/background, Square/Flat, Classes/Styles), content/HTML/media and raw Custom CSS in their original owners.
- One stable semantic class per module, with any generated native scope supplied by the destination compiler. Keep Section `&` syntax in Section Custom CSS. Never put compiled `.section-...-sourceID` output into Page CSS.
- CSS dependency closure: identify inherited Theme typography, native roles, button/focus treatment, page-level aliases, generated IDs and shared selectors. Extract only required rules into the module/global package. Hash every artifact and record tests/evidence.
- Destination data mapping: products/categories/channels, movies/showings, membership products/URLs, forms/recipients, images and links. Classify each field as literal approved content, local destination reference, native palette role, preset, or unresolved dependency.
- Installation method and evidence: native recreation, a verified carrier Page import, or another separately observed capability. Include Library link/unlink policy and destination global-style compatibility.

## Why full stylesheets cannot be combined

Current variant Page/Site CSS includes broad `[class*="section-"]` selectors, differing aliases such as D/E `--v-*`, source header/page selectors and inherited Theme behavior. Concatenating selected variants can make the last stylesheet silently repaint earlier choices. Section/module tests must demonstrate style independence and explicit ownership, not merely absence of a syntax error. Never define native `--q-primary` etc. as aliases back to module variables; that can create an inherited custom-property cycle.

Build one intentional destination Theme/header package and module-scoped Section packages. Keep native Primary/Secondary/Dark/Background inputs; use readable derived surfaces where needed. Preserve status/error semantics. Current Header→Dark and Accent→Secondary behavior is part of the retained adapter contract. New independent Header/Accent behavior requires its own scoped correction and QA; choosing colors is not proof of that correction.

Fonts, slants, decorative angles and collage geometry are maintained presets unless the native control has been verified. Odd membership HTML needs explicit semantic classes for tier roles; its tier labels were native `<p class="od-club__tiername">`, not assumed heading tags. Preserve real source markup/copy while extracting a module.

## Concrete output for a blocked option

For each blocked choice, produce an actionable row:

| Field | Required output |
| --- | --- |
| Choice | Stable option ID, canonical component, source editable/published identities and export SHA. |
| Existing evidence | Actual raw fields/artifacts available; missing settings/content/media. |
| Native construction | Widget type(s), ordered child list, intended stable class and owner of each setting/style. |
| Isolation work | Which Page/Theme rules must be extracted, variables removed/rebound, globals supplied once. |
| Content work | Approved source copy/media to retain, destination records to create/rebind, permissions still needed. |
| Proof | Authorized isolated draft + save/readback, compiled current scope, destination catalog behavior and mixed-page compatibility. |
| Acceptance | Desktop/phone previews, palette/overlay states, empty/populated states, links and explicit consumer-only limitations. |

Never make all modules appear ready by defaulting unknown properties or reducing a dynamic widget to static screenshot/HTML. A user may authorize packaging as the next concrete step; otherwise deliver this local plan and the exact blockers without claiming a draft site was built.

## Native assembly when ready

1. Verify exact new target and approved Starting Template. Inventory seeded Theme, Pages, Global Widgets, Navigations, data and hosting. Do not delete seeded objects unless separately authorized.
2. Prepare approved sample-content seed and destination dependencies. Do not reuse source record IDs as configured destination references.
3. Save intentional Theme/header/navigation settings with current binding caveats. Record immediate-effect global settings separately from unpublished Page drafts.
4. Choose final Page creation titles and all native Section Names before initial Create. Read actual slugs and scopes back. Never promise that a later title change fixes a generated slug.
5. Recreate module fields through native UI or an actually verified import method. Capture destination identity mapping and exact raw CSS readback. Save each Section independently; do not paste a compiled whole-Page stylesheet into the raw field.
6. Put homepage modules in selected order. Use only one food menu in the final slot unless separately requested; adjacent native menus can leave an earlier floating category bar over the next one.
7. Build requested showcase pages from their same module packages; common navigation remains site-global. Reopen ordering and compare the complete actual child list with the plan.
8. For Library imports, immediately use **Unlink**, Save and verify **Not Linked** before local customization. Disabling Library Updates alone retains a link; Force Update can still refresh it. Leave a master linked only when explicitly requested.
9. Reopen Page/Sections; confirm saved state, current generated scope, correct typography and no unexpected generated-ID dependency. If an authorized internal rename exposes stale scope, preserve CSS and investigate the retained pilot's comment-only re-save pattern; do not blindly change names repeatedly.

Keep the source, library master and unrelated existing destination records unchanged. Record partial progress honestly if a native capability or data dependency prevents completion; do not automatically publish, import unrelated data or trigger a deployment to work around it.
