# Module packaging and assembly

## Package the actual editable fields

Build a readiness row for each selected stable `optionId`, including globals and optional modules. Separate these levels: source screenshot checked; native fields captured; isolated module saved/read back; destination assembly verified; consumer desktop/phone/theme behavior verified. Do not collapse them into a generic “verified” flag.

A portable package needs:

- Native widget type and exact final internal Name plan for each ordered child Section; composite heroes A/C can contain more than one Section.
- Widget main settings, Section settings (visibility, devices, scheduling, width/margins/background, Square/Flat, Classes/Styles), content/HTML/media and raw Custom CSS in their original owners.
- One stable semantic class per module, with any generated native scope supplied by the destination compiler. Keep Section `&` syntax in Section Custom CSS. Never put compiled `.section-...-sourceID` output into Page CSS.
- CSS dependency closure: identify inherited Theme typography, native roles, button/focus treatment, page-level aliases, generated IDs and shared selectors. Extract only required rules into the module/global package. Hash every artifact and record tests/evidence.
- Destination data mapping: products/categories/channels, movies/showings, membership products/URLs, forms/recipients, images and links. Classify each field as literal approved content, local destination reference, native palette role, preset, or unresolved dependency.
- Installation method and evidence: native recreation, a verified carrier Page import, or another separately observed capability. Include Library link/unlink policy and destination global-style compatibility.

## Why full stylesheets cannot be combined

Current variant Page/Site CSS includes broad `[class*="section-"]` selectors, differing aliases such as D/E `--v-*`, source header/page selectors and inherited Theme behavior. Concatenating selected variants can make the last stylesheet silently repaint earlier choices. Section/module tests must demonstrate style independence and explicit ownership, not merely absence of a syntax error. Never define native `--q-primary` etc. as aliases back to module variables; that can create an inherited custom-property cycle.

Build one intentional destination Theme/header package and module-scoped Section packages. Keep native Primary/Secondary/Dark/Background inputs; use readable derived surfaces where needed. Preserve status/error semantics. Current Header→Dark and Accent→Secondary behavior is part of the retained adapter contract. New independent Header/Accent behavior requires its own scoped correction and QA; choosing colors is not proof of that correction.

Fonts, slants, decorative angles and collage geometry are maintained presets unless the native control has been verified. Odd membership HTML needs explicit semantic classes for tier roles; its tier labels were native `<p class="od-club__tiername">`, not assumed heading tags. Preserve real source markup/copy while extracting a module.

## Native assembly when ready

1. Verify exact new target and approved Starting Template. Inventory seeded Theme, Pages, Global Widgets, Navigations, data and hosting. Do not delete seeded objects unless separately authorized.
2. Prepare approved sample-content seed and destination dependencies. Do not reuse source record IDs as configured destination references.
3. Save intentional Theme/header/navigation settings with current binding caveats. Record immediate-effect global settings separately from unpublished Page drafts.
4. Choose final Page creation titles and all native Section Names before initial Create. After Page Create, close and reopen from the inventory before adding Sections; record the loaded editable identity. Read actual slugs and scopes back. Never promise that a later title change fixes a generated slug.
5. Recreate module fields through native UI or an actually verified import method. Capture destination identity mapping and exact raw CSS readback. Save each Section independently; do not paste a compiled whole-Page stylesheet into the raw field.
6. Put homepage modules in selected order. Use only one food menu in the final slot unless separately requested; adjacent native menus can leave an earlier floating category bar over the next one.
7. Build requested showcase pages from their same module packages; common navigation remains site-global. Reopen ordering and compare the complete actual child list with the plan.
8. For Library imports, immediately use **Unlink**, Save and verify **Not Linked** before local customization. Disabling Library Updates alone retains a link; Force Update can still refresh it. Leave a master linked only when explicitly requested.
9. Reopen Page/Sections; confirm saved state, current generated scope, correct typography and no unexpected generated-ID dependency. If an authorized internal rename exposes stale scope, preserve CSS and investigate the retained pilot's comment-only re-save pattern; do not blindly change names repeatedly.

Keep the source, library master and unrelated existing destination records unchanged. Record partial progress honestly if a native capability or data dependency prevents completion; do not automatically publish, import unrelated data or trigger a deployment to work around it.

## Native Page and Custom editor safeguards

These guards come from the Showcase draft pass. They concern observed INDY surfaces, not limitations of CSS or HTML generally.

**Create into the normal editable Page.** A new Page Create can leave the form on its base record while normal inventory Edit opens a different editable child. Close the initial form and reopen through the inventory before adding any Section. Wait until the expected saved Title and slug are populated and the Section list has settled; an initial accessibility snapshot can show defaults, blank fields or No Sections while loading. Record both IDs and the actual editable Section list. The inventory/base Section count can remain zero even when the editable Page is populated. Do not recreate from that count alone.

If earlier construction attached Sections to the base version, retain that mapping as historical/inactive evidence. Inspect the normal editable Page before corrective assembly. Populate only an actually empty or incomplete authorized editable record; leave base Sections untouched rather than deleting or publishing them as cleanup. Close and reopen the whole Page after assembly to verify each expected editable Section ID and body persists.

**Set Type before the final Name.** A native Type change can overwrite an already entered Name with the widget's default (for example, Showtimes). Choose Type, let its controls finish rendering, then set and read back the final internal Name before Create. Do not rely on a Name entered before the Type change; generated CSS scope depends on the saved Name.

**Verify the Custom body at three boundaries.** After Type and final Name, use native GrapesJS **Edit Code** (`title="Edit Code"`). Enter the approved body in the HTML editor. On an initially empty Section, keep code-editor CSS empty and enter the portable stylesheet in **Section Settings → Custom CSS**. After reopening, the code editor can display that Section stylesheet as integrated GrapesJS CSS; this is not permission to clear it.

For CodeMirror, use its visible native UI: focus the HTML editor, select all, then fill its textarea through the documented locator API, or paste while holding exclusive clipboard ownership. The tested Windows UI sequence is textarea `press("Control+A")` followed by `fill(bodyHtml)`; fill without select-all can insert before the existing document. Do not call CodeMirror/GrapesJS application internals. Browser agents share a clipboard, so serialize clipboard write/paste pairs across them. After entry, read the visible CodeMirror text and confirm the intended body before **Save Code**. Then confirm the expected heading, text, classes and links in the GrapesJS iframe before the Section Save. Finally, close/reopen the Page and Section and confirm the actual body again. A valid CSS readback with an empty body is a failed save; repair that same Section rather than creating a duplicate.

**Round-trip Custom/GrapesJS CSS.** The observed GrapesJS parser can rewrite comma-containing `:is(...)` selectors and variable-containing background/border/outline shorthands into broken selectors or declarations. For Custom Sections using this parser, use separate explicit scoped selectors, `background-color`, and border/outline width, style and color longhands. Keep native `&` scope and stable module classes. Native serialization can expand padding/margins and normalize whitespace; compare meaning as well as bytes. Reopen and inspect the saved CSS for missing rules, unsupported `:is(...)` remnants and empty values such as `color: !important`; verify the resulting DOM scope and computed layout. Native widget fields and Theme stylesheets can retain different syntax; validate each actual owner rather than imposing this parser limitation on every CSS surface.

**Treat import, upload and data references separately.** A Library Item chooser showing source products does not mean those Items exist locally. The Showcase food import returned Code 903 and a settled reload still showed **No Items**, including after the smaller single-Item attempt. No food/product portability was established. Categories and an Item Class could be saved while the Item editor's required class reference chooser remained unresolved. Record that gap; do not bypass required references, substitute source IDs or claim a populated menu. For native media uploads, identify the exact destination field and choose its first/main **Image** uploader deliberately; similar controls for background, thumbnail or other image slots are not interchangeable. Read back the selected asset in that field.

If native Create/import returns Code 903 or another server error, first inspect the authorized scoped inventory after a settled reload; the operation may already have created a record. A Save/Save and Close can also return Code 903 after fields persist, so reopen and compare the expected fields/order before retrying. Resolve the unknown outcome before another mutation. A smaller import attempt that also fails is evidence of a capability gap, not a reason for repeated imports or an undocumented API workaround.
