# Picker build brief

`Build brief` downloads `fd-template-picker/v3` JSON. It is a requested design and a source-evidence record, not permission to create a Circuit/Site, provision hosting or publish. Its `buildContract.destination` is always `null`, `destinationAuthorizationRequired` is `true`, and `publicationPolicy` is `draft-only`.

## Palette and compatibility

The reader accepts v1, v2 and v3 selections. `brandColors` remains a normalized Primary/Secondary mirror. `palette.version: 1` contains thirteen `roles`: `primary`, `secondary`, `header`, `accent`, `dark`, `background`, `positive`, `negative`, `info`, `warning`, `splashBackground`, `seatSelected`, `seatAvailable`.

`palette.nativeBindings` names each Admin field, known CSS variable, current template role and verification status. Header currently maps to Dark and Accent to Secondary in native adapters; their independently requested values must not be represented as already supported. Unverified splash/seating CSS variables are `null`. Suggested starter values are not captured target-site values or canonical INDY defaults.

The first-step confirmation fingerprints every palette role, the current binding contract and the three font choices. Old matching color confirmations can migrate with default fonts; component choices and matching component confirmations survive. Later palette or font edits invalidate the first-step confirmation. Both Primary/Secondary and Dark/Background must reach unrounded 3:1; a pair below 4.5:1 also requires the palette-bound acknowledgment. Rendered states and derived combinations need separate checks.

## Typography

`typography` is an additive `{ schema: "fd-typography/v1", roles: { headings, body, interface } }` selection. Each value is an allowlisted ID: `arial`, `verdana`, `tahoma`, `trebuchet-ms`, `georgia`, `times-new-roman` or `courier-new`. Defaults are `georgia`, `arial`, `arial`. Legacy briefs may omit typography.

`typographyBindings` describes each requested family, CSS fallback stack and element role. These are build requests, not verified native settings. The destination's editor mapping, any modular CSS needed for the third role, and rendered desktop/phone text must be checked during the build. Fonts are resolved from the visitor's device; the picker loads no external font assets. The validator rejects supplied unsupported font IDs instead of applying arbitrary strings.

Saved selections and links carry the raw role IDs. The summary and review show family names. Only the inline sample changes; template screenshots and live demo sites retain their original fonts. Changing fonts preserves a still-valid palette acknowledgment but requires confirming Colors & fonts again.

## Build contract

`buildContract.version: 1` includes:

- `catalog.sha256`: SHA-256 of the exact loaded catalog bytes, plus its generation timestamp.
- `moduleIndex.sha256` and `schema`: exact registry bytes and `fd-picker-module-index/v1`.
- `checklistComplete`: true only when the full palette, three font choices and exactly one selected option per required component match their recorded confirmations.
- `componentOrder`: Navigation, Hero, Food, Private Parties, Membership and Contact in the customer sequence.
- `modules`: included stable `optionId`, component/slot, source references, installation method, bounded readiness, artifact paths and SHA-256 values, and known limitations.
- Explicit target authorization, dependency resolution, artifact validation and draft preview preflight requirements.

Every native ID in the brief is a **source reference**. Existing top-level Section metadata is retained for compatibility and marked `sourceIdsOnly: true`; `sourceReference` groups the original Page/Section IDs and URL. These must never become destination IDs by inference.

`data/build-modules.json` is generated by `node scripts/build-module-index.mjs`. Its `catalogSha256` must match the loaded catalog. Most options carry source Page CSS references and **unverified portability**. These source artifacts are not standalone Section installation packages.

Clubhouse Food has a separate portable Section package: verified one-section Library Page transfer/unlink and native recreation/ordering inside an existing Page, within recorded Admin-preview limits. Those historical manifest flags and the existing readiness enum remain unchanged. A separately named `liveIndependentCopyVerification` now records the later published independent copy: current native palette, three columns at 1536px, one at 390px, seven loaded photos and zero menu/document overflow in both. Live-phase journal, measurements, category evidence and findings carry separate hashes.

The old carrier/Admin phase's pending consumer checks are historical limits, not the current status of the published independent copy. The mobile category jump reaches Desserts, but its dropdown label can remain Drinks until further scrolling. Direct Library Section insertion, cross-page copying, arbitrary palette changes, physical devices, Mobile App, checkout, catalogue availability rules and controlled empty state remain unverified. Do not infer that other options share K's readiness.

## Consumer responsibilities

An installation skill must validate schema, confirmations, digests and module capability; obtain an exact separately authorized target and operation scope; resolve destination catalog, navigation, booking, media and form bindings; map newly created native IDs; and stop at the authorized draft boundary. A passing screenshot review or complete customer checklist does not certify that a module is portable or grant publishing/hosting authority.

Screenshots retain original colors and provenance. Color sample cards demonstrate base text pairs only. No cross-origin native preview bridge is assumed.
## Optional recolored previews

The current screenshots retain their original pixels. A stylesheet on the picker cannot directly override a remote INDY iframe: separate origins restrict access to the embedded document ([MDN same-origin policy](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy)). `!important` does not change that boundary.

A future preview can use a small, cooperative preview-only handler on the template site to receive the requested palette through [`postMessage`](https://developer.mozilla.org/en-US/docs/Web/API/Window/postMessage), validate the exact sender and color values, and apply temporary variables inside that document without saving Admin settings. Embedding permission and the actual variable mappings must be verified first. A locally rendered approximation is another option. Neither route is implemented or required for this rollout.
