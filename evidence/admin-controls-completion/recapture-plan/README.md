# Native picker recapture plan

This is a capture plan and validation helper, **not capture evidence**. No actual images or catalog records have been changed by its preparation.

The actual customer workflow currently exposes **66 distinct choices**: 7 navigation, 11 hero and 12 each Food & Drink, Private Parties, Membership and Contact Us. `customer-captures.json` is generated by importing the same `createWorkflow()` used by the picker, preserving reviewed eligibility and the Standard navigation group. It records every required option's current source identity and canonical image destination.

The minimum is **66 genuine native desktop element clips**. Five additional H–L navigation clips would refresh the duplicate source evidence, yielding 71 core clips. They must remain grouped under Standard. Concrete's hero is currently excluded because its image is not rendered; do not create a blank substitute or turn that absence into a customer choice. The other non-core inventory previews are separate from this customer flow.

## Capture sequence

1. Finish the named source saves/publishes and verify the actual public routes. Restore the current native palette after the second-palette test. Keep phone and temporary-palette QA images separate.
2. Work one published variant at a time. Read its current URL, page identity, named section wrappers, actual section IDs and DOM rectangles. The plan's previous IDs/selectors/coordinates are hints only: publication can change IDs, and text/caption adjustments can change height.
3. At document top, take the actual native header clip with all its real navigation items and utilities visible. Concrete is a 240px sidebar; use its full current header rectangle. Standard needs G's representative clip once.
4. For each required content option, match the actual semantic section. Hero alternatives J/K/L are introductory editorial sections, while B's Playbill is optional programming and **not** the dedicated Private Parties option. Preserve merged multi-section option identity where the catalog currently has multiple `sectionIds`.
5. Use native JPEG element clips from the browser and record the fresh document coordinates and actual raster dimensions. Include full section content; neither a fixed header covering content nor a clipped last row is acceptable. Do not infer width from the browser viewport: Concrete content excludes the sidebar, and native scrollbars can make document width fractional.
6. Inspect each actual clip for its matching component/label, complete content, readable copy and absence of browser editor/hover controls. Record a dated visual review bound to that exact JPEG SHA-256, with notes and evidence. If published section IDs changed, explicitly set `sourceIdentityVerified:true` only after checking the same semantic source.
7. Validate the manifest read-only, then ingest a complete 66 clip batch, or use `--allow-partial` for an explicitly reviewed subset. Source journal links, exact raw bytes and a catalog rollback backup are retained.

No temporary CSS, fixture data, image recoloring, caption edits, stitching or re-encoding is allowed. `scripts/process-captures.py` remains useful for its existing full-page/tile provenance pipeline; this new direct-clip path avoids re-saving already correct native JPEGs. It uses the existing `applyCaptureCorrections()` validator, which preserves display names, Admin names, draft IDs, dependencies, Library fields, equivalence groups, semantic parity and every unrelated record.

## Read-only browser resolver

`scripts/resolve-admin-controls-capture-plan.mjs` exports the self-contained `resolveAdminControlsCapturePlan(plan, document, runtime)` function. Serialize that function through the **existing supported read-only browser evaluation API** after inspecting the current public DOM. Do not install a script, create a new browser automation connection, or alter the page. The optional runtime object supplies the Node-side observation timestamp and actual observed scroll offsets when the restricted DOM adapter omits them. In the browser, the function follows the acceptance sampler's existing `getComputedStyle`, `innerWidth`, `innerHeight`, `getAttribute`, `parentElement` and native rectangle patterns. It does not depend on `Set`, `URL`, `Date`, `document.defaultView`, `classList`, or attribute enumeration.

The resolver matches the actual URL and visible native page wrapper, then matches current section IDs. If publication changed an ID, it can suggest only an exact prior class-name stem, explicitly requiring semantic review. It refuses missing/ambiguous sections, reused elements, nonconsecutive merged source sections, unexpected page IDs, missing scroll proof, incomplete images, loading documents and phone viewport assets. It returns actual source/viewport rectangles, an outward-rounded document clip, native palette, fresh exact selectors and the current header/sidebar rectangle. It never automatically approves semantics or claims that a public route has been verified as published.

Pass the function the full plan or its `required` array. Record its result and inspect `blockers`, each `clip.blockers`, `sourceIdentityChanged`, headings and image completeness before using a clip. Always confirm the coordinate convention in the active browser API: packaged browser docs describe native JPEG bytes and `screenshot({clip:{x,y,width,height},fullPage?})`, but do not specify the coordinate space. The resolver deliberately returns both document and viewport rectangles, scroll and optional scale metadata. Use the proven native document-clip method; do not assume that a full-page image can be substituted for an element clip. Re-observe if a viewport change, scroll, reload or layout change occurs.

In this 25 October native capture cycle, root verified `tab.screenshot({clip})` for the actual document rectangles. Combining `fullPage:true` with `clip` repeatedly timed out, so the completed native clips use the clip option alone. Moving the native pointer to the verified outer scrollbar gutter removed pointer marks; affected hero clips were retaken rather than pixel-edited.

Seven focused resolver tests cover merged bounds, changed IDs, ambiguous/nonconsecutive sources, Concrete sidebar geometry, wrong target/device/loading state and serialization without unsupported globals. They are local fixture checks, not a live browser execution claim.

```text
node --test tests/resolve-admin-controls-capture-plan.test.mjs
```

## Validate and ingest

```text
python scripts/ingest-admin-controls-captures.py evidence/admin-controls-completion/recapture-plan/customer-captures.json actual-native-manifest.json
python scripts/ingest-admin-controls-captures.py evidence/admin-controls-completion/recapture-plan/customer-captures.json actual-native-manifest.json --apply
```

Validation is the default and writes nothing. It checks target, published/restored-palette declarations, actual identity, current destination, required coverage, fresh selector/rectangle fields, JPEG format, raster dimensions, X/Y scale, full containment, no fixtures/temporary appearance changes and review hashes. It also runs the existing correction validator using raw bytes before any canonical image is replaced.

Application first stages all raw/canonical image bytes, updated catalog and provenance files. Ordinary file-operation failure rolls canonical images and catalog back. Successful application retains raw images, observations, dated reviews, an immutable byte-identical native journal snapshot and its hash, `catalog.before.json` and an ingestion record under a unique `evidence/admin-controls-completion/captures/<batchId>/` directory. Evidence retains both the live journal link and its immutable snapshot, so later journal status updates do not invalidate the captured hash. It byte-copies the native JPEGs; it performs no image edits. A `needs-review` or `rejected` image remains explicitly unavailable to the customer flow.

The plan itself is current as of its catalog hash. A changed source page or destination requires rebuilding/reviewing the plan. A changed published section ID requires an explicit semantic identity review. A timestamp, hash or successful script run does not prove that the screenshot matches its label; the real pixel review remains required.

Ten focused tests cover identity/hash preservation, changed IDs, altered/partial pixels, duplicate/incomplete batches, omitted/resized clips, draft/phone/temporary-palette rejection, exact byte copies, Unicode semantic metadata, catalog-only encoding repair and failure rollback. They use temporary synthetic test fixtures that never enter the real catalog.


## Windows UTF-8 catalog repair

Node emits UTF-8. The Python subprocess explicitly uses strict UTF-8 for stdin, stdout and stderr; relying on a Windows locale decoder can corrupt semantic labels such as `B · Rep` throughout the output catalog. The Unicode regression verifies middle dots, accents, curly quotes/apostrophes, a narrative newline, arrows and non-Latin source labels.

For an already applied batch affected by the older locale-decoding bug, the helper has a catalog-only repair mode. It rebuilds from that batch's immutable `catalog.before.json`, retained observations/reviews and raw images. It verifies the raw/canonical image hashes and native journal snapshot, checks every original non-capture field across all options, and runs the existing correction validator with explicit UTF-8. It does not recreate the batch or re-encode/replace image files.

```text
python scripts/ingest-admin-controls-captures.py repair-catalog-utf8 evidence/admin-controls-completion/captures/ACTUAL-BATCH-ID
python scripts/ingest-admin-controls-captures.py repair-catalog-utf8 evidence/admin-controls-completion/captures/ACTUAL-BATCH-ID --apply
```

The first command validates without writes. The second saves the current catalog bytes as `catalog.before-utf8-repair.json`, atomically writes the corrected UTF-8 catalog and records `utf8-repair.json`. Existing batch inputs and image bytes remain unchanged. If the catalog already matches the reconstructed UTF-8 output, the command is a no-op.
